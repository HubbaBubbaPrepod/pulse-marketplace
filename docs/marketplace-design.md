# Pulse Marketplace — проект первой версии

Дата: 14 октября 2026. Статус: сценарий и стек согласованы; технический план подготовлен для проверки. Реализация и развёртывание ещё не выполнены.

## Согласованная задача

Разработчик публикует модуль на GitHub. Marketplace обнаруживает его, проверяет структуру и передаёт конкретную версию модераторам. После одобрения модуль доступен на сайте и в добровольно подключаемом каталоге Pulse Monitor. Пользователь скачивает JSON вручную либо устанавливает выбранную версию из своего монитора.

Агент не обращается к marketplace. Ручная установка JSON продолжает работать без внешнего каталога. Проверка не означает гарантии безопасности нативной программы.

Вход: GitHub, Google, email и пароль. Для чтения каталога и скачивания пакетов вход не требуется. Автору не нужно создавать аккаунт для обнаружения репозитория.

## Состав и размещение

- `pulse-website` остаётся статическим лендингом на GitHub Pages. Его каталог ссылается на marketplace.
- Новый самостоятельный репозиторий `pulse-marketplace`: Next.js для публичного каталога и кабинетов, Nest.js API для обнаружения, проверки, модерации, аутентификации и загрузок; PostgreSQL для метаданных и аккаунтов, отдельное файловое хранилище для проверенных JSON-пакетов.
- Предлагаемый адрес: `marketplace.hubba-cloud.ru`. Для него потребуется отдельная DNS-запись и действительный сертификат.
- На выбранном сервере запускаются Next.js, Nest.js и PostgreSQL за одним HTTPS reverse proxy. API и база не публикуются отдельными открытыми портами; браузер обращается к API того же origin. Планировщик обнаружения работает внутри Nest.js; PostgreSQL advisory lock исключает наложение обходов. Redis и отдельного сервиса очередей в первой версии нет.
- `pulse-monitor` получает вкладку marketplace и серверные маршруты каталога/установки. `pulse-agent` сохраняет текущий протокол модулей.
- `pulse-module-docker` получает маркер обнаружения и topic. Его существующий пакет используется как первый реальный кандидат, но не становится одобренным автоматически.

Динамический каталог не размещается целиком на GitHub Pages: новым карточкам, входу и очереди модерации требуется сервер. Переносить готовый лендинг с Pages не требуется.

## Обнаружение на GitHub

Автор добавляет topic `pulse-module` и файл `pulse-marketplace.json` в корень репозитория:

```json
{
  "schemaVersion": 1,
  "moduleId": "docker",
  "packageAsset": "docker-module.json"
}
```

Этот файл описывает обнаружение и не передаётся установщику монитора. Он не меняет `schemaVersion: 1` и `protocol: 1` текущего пакета. Имя asset должно быть простым именем файла, без URL, каталогов или обхода путей.

Цикл раз в 30 минут:

1. Искать публичные неархивные репозитории с topic `pulse-module`; обходить страницы результатов, учитывать лимиты GitHub и неполные результаты.
2. Для каждого репозитория прочитать маркер, затем опубликованные обычные releases. Draft и prerelease не публиковать в первой версии.
3. Зафиксировать числовые GitHub repository/release/asset ID, tag и commit SHA. У releases разрешать только tags, соответствующие версии пакета с необязательным префиксом `v`.
4. Прочитать маркер также из зафиксированного release commit. Изменение маркера в default branch не подменяет содержимое старого релиза.
5. Скачать указанный asset только из того же репозитория, без произвольных адресов автора.
6. Проверить пакет и сохранить его точную копию и SHA-256. Добавить кандидата в очередь.

Повторный обход идемпотентен. При изменении asset, tag, commit или владельца создаётся новая ревизия кандидата; одобрение прежней ревизии не наследуется. Для уже опубликованного owner/moduleId/version запрещено одобрять другой hash: автор должен выпустить новую версию. Исчезновение репозитория не удаляет сохранённую опубликованную копию автоматически. Уведомление модератору показывает изменение источника.

Первый запуск делает полный поиск. Последующие циклы повторяют поиск и отдельно проверяют уже известные репозитории. При достижении ограничения поиска 1000 результатов запросы разделяются по диапазонам даты создания. На 429/лимиты API применяются Retry-After/reset и ограниченный backoff; последний одобренный каталог сохраняется. Токен для чтения публичного GitHub хранится только на сервере, без права изменения репозиториев.

## Проверка пакета

Проверка совместима с `backend/modules.go` и `docs/MODULES.md` монитора:

- один JSON-объект, schema/protocol 1, допустимые ID и версия;
- до 32 полей, 16 представлений; существующие типы полей и представлений;
- `linux-amd64`, `linux-arm64`, `windows-amd64`;
- до 16 MiB на декодированный бинарник и 48 MiB суммарно; ограничение тела пакета 68 MiB;
- SHA-256 каждого бинарника и заголовок ELF/PE соответствующей архитектуры;
- `moduleId` маркера совпадает с ID пакета; версия совпадает с release tag;
- строки и описание показываются как текст. Авторские HTML, JavaScript и внешние iframe не исполняются.

SHA-256 всего JSON хранится отдельно от внутренних SHA-256 бинарников. При наличии digest GitHub он тоже проверяется, но самостоятельно вычисленный digest остаётся обязательным.

Загрузчик ограничивает размер, время, число редиректов и число кандидатов за цикл. Разрешены только необходимые HTTPS-хосты API/GitHub release assets; приватные, loopback и link-local IP запрещены на каждом соединении и редиректе. Токен GitHub не пересылается на хосты скачивания. Нативные файлы не запускаются ни сканером, ни публичным API.

## Модерация и идентичность

Идентификатор карточки — `owner/moduleId`. Внутренняя привязка к числовому repository ID сохраняется при переименовании репозитория. Один репозиторий публикует один moduleId в первой версии. Перенос владельца требует повторного рассмотрения новых релизов.

Текущий монитор использует плоский `id`; два пакета разных авторов с одинаковым ID конфликтуют. Marketplace явно показывает автора и внутренний ID. Монитор отклоняет установку другого происхождения поверх уже установленного ID. Новое пространство ID в агенте в этой версии не вводится.

Состояния ревизии: `pending`, `approved`, `rejected`, `withdrawn`. Только approved входит в публичный каталог и доступно для обычного скачивания. Изменение решения фиксирует модератора, время и обязательный комментарий.

Очередь показывает исходники на закреплённом commit, пакет, платформы, права, результаты автоматической проверки, изменения относительно предыдущей версии и историю решений. Одобрение относится к одной точной ревизии и hash. Релиз с проваленной автоматической проверкой нельзя одобрить.

Модераторы проверяют исходники, разрешения и происхождение бинарников; при необходимости проводят ручное тестирование в отдельной изолированной среде. Кнопка одобрения не запускает бинарник. UI не обозначает модуль как «безопасный»: показывает пройденные проверки и дату модерации.

Обычный модератор должен привязать GitHub и не может одобрять собственный репозиторий. Администратор может одобрять модули через вход по паролю или провайдеру, включая собственные, без отдельного GitHub-аккаунта. Проверки хеша, автоматической валидации, сохранённого пакета и состояния ревизии обязательны для всех; решение фиксируется в аудите. Администратор назначает модераторов. Начальные административные права задаются при приватной настройке сервиса, а не первому произвольному посетителю публичной регистрации.

Withdrawn скрывает версию и блокирует новую установку. Уже установленные сборщики не останавливаются и не удаляются удалённой командой marketplace. После добровольного обновления каталога монитор показывает предупреждение.

## Аккаунты

Роли: reader/author, moderator, administrator. Самостоятельная регистрация не даёт права модерации. GitHub-авторство подтверждается GitHub-входом и доступом к конкретному репозиторию, а не текстом поля author в пакете.

GitHub и Google: серверный OAuth/OIDC flow, одноразовые state, PKCE где поддерживается, фиксированные redirect URI, проверка issuer/audience/nonce/подписи для Google. Идентификатор пользователя — provider ID/sub. Совпадение email само по себе не связывает аккаунты; связывание требует входа в существующий аккаунт и подтверждения второго провайдера.

Email: подтверждение адреса и восстановление через одноразовые ограниченные по времени токены. Без настроенной отправки писем email-регистрация и восстановление в production отключены с понятным сообщением. В новом marketplace пароли хешируются scrypt из `node:crypto` с уникальной случайной солью, параметрами N=131072, r=8, p=1 и ограниченной параллельностью; существующий bcrypt монитора не меняется. Ответы входа/восстановления не раскрывают существование адреса.

Сессии имеют срок жизни, хранятся на сервере, cookie HttpOnly/Secure/SameSite; изменения защищены от CSRF. Ограничение частоты применяется к входу, регистрации, восстановлению и служебным операциям. Выход/отзыв роли действует на следующий запрос.

Кабинет автора показывает обнаруженные репозитории, состояния версий и замечания модераторов. Добавление репозитория вручную может ускорить проверку, но не обходит маркер, проверку пакета или модерацию.

## Данные и API

Первая версия рассчитана на один экземпляр API. Репозитории, ревизии, решения модераторов, аккаунты, связи OAuth, сессии и аудит хранятся в PostgreSQL. Схема изменяется версионированными SQL-миграциями; для доступа используется драйвер `pg`, без ORM и автоматического изменения схемы при запуске. Проверка прав и изменение решения выполняются в одной транзакции с блокировкой строки ревизии. Уникальные ограничения предотвращают повторное обнаружение и дубли аккаунтов.

Пакеты хранятся в приватном постоянном каталоге отдельно по SHA-256. Временный файл, вычисление digest, fsync и атомарная публикация завершаются до добавления доступной для скачивания записи в PostgreSQL. Публикация ревизии не разрешается при отсутствии файла. После рестарта все решения и файлы сохраняются. Резервное копирование включает базу и пакеты; восстановление проверяет наличие файлов для опубликованных ревизий. База не заменяется пустой при ошибке подключения или миграции.

Публичный API `/api/v1`:

- `GET /catalog?query=&platform=&cursor=` — ограниченные страницы одобренных карточек, без бинарников и личных данных;
- `GET /modules/{owner}/{id}` — карточка и одобренные версии;
- `GET /modules/{owner}/{id}/versions/{version}` — digest, размер, платформы, происхождение, права и результаты проверки;
- `GET /packages/{sha256}` — неизменяемые байты только опубликованной неотозванной ревизии;
- `GET /health` — готовность без секретов.

Каталог имеет revision/ETag. Ответ списка не обещает, что package ещё доступен: установка отдельно проверяет действительность выбранной версии. Статусы и проверки представлены отдельной оболочкой каталога, не дополнительными неизвестными полями установочного JSON.

Приватные API: auth, собственные публикации, очередь модерации, одобрение/отклонение/отзыв, роли и ручной запуск сканирования. Все права проверяются сервером на каждом запросе. Аудит не содержит паролей, токенов, содержимого сессий и конфигурации наблюдаемых серверов.

## Каталог внутри Pulse Monitor

Вкладка показывает описание доступа и кнопку включения. Подключение по умолчанию отключено; простое открытие вкладки не делает запрос к marketplace. Настройка сохраняется в данных монитора. Нет фоновых внешних запросов без включения.

При включении монитор загружает публичный каталог по фиксированному HTTPS-адресу. Не отправляет ID/имена серверов, метрики, логи, токены агентов, конфигурацию модулей, email или внутренние адреса. Публичный сервер при соединении видит IP монитора. Это указано рядом с переключателем.

Установка: выбрать версию → посмотреть автора/источник/права/платформы → явно подтвердить → backend монитора повторно проверить текущий статус, размер и SHA-256 пакета → применить существующую валидацию и атомарный установщик → отдельно предложить включение для узла. Browser и marketplace никогда не получают пароль монитора или токен агента. Сайт marketplace не вызывает автоматически локальные URL пользователя.

Пакет скачивается только из настроенного доверенного каталога. ID и версия не превращаются в произвольный URL. Конкурентное изменение установки даёт конфликт; частичная загрузка не заменяет существующий пакет. Установленная версия и происхождение сохраняются локально.

При отключении отменяются ожидающие загрузки и прекращаются дальнейшие запросы. Недоступность marketplace не мешает мониторингу, ручной установке или уже установленным модулям. Проверку обновлений пользователь включает отдельно; автоматической установки обновлений нет.

## Интерфейс

Next.js, RU/EN, светлая/тёмная темы и motion в стиле Pulse с reduced-motion и реальной skeleton-загрузкой. Публичные карточки имеют серверный HTML, canonical, hreflang, sitemap и структурированные данные без выдуманных рейтингов.

Основные экраны: каталог с поиском/платформами, карточка с версиями и правами, вход, кабинет автора, очередь и детальная проверка модератора, управление ролями для администратора. Ошибки и пустые состояния не подменяются demo-модулями.

### Интерактивный фон hero

Референс: [Xiaomi MiMo](https://mimo.xiaomi.com/), блок `heroSection-QyeJcW`, проверен в браузере 14 октября 2026. За указателем движется контрастная маска с инерцией: при быстром движении она вытягивается и раскрывает второй слой с другим фоном и текстом. В DOM референса второй слой ограничен изменяемым `clip-path: polygon(...)`.

В hero marketplace повторить механику с оформлением Pulse:

- Тёмная тема: маска раскрывает светлый слой; светлая тема: тёмный. Фоновый узор использует Pulse вместо MiMo. Заголовок и его читаемость сохраняются.
- Маска плавно следует за указателем и вытягивается по направлению движения; после остановки возвращается к округлой форме. Эффект ограничен hero и не перехватывает нажатия, выделение текста или фокус элементов.
- Анимация включается для устройств с точным указателем и hover. На сенсорных устройствах и при `prefers-reduced-motion: reduce` показывается статичный фон.
- Декоративный слой скрыт от вспомогательных технологий; основной заголовок остаётся единственным доступным заголовком. Анимация останавливается вне видимой области, при скрытой вкладке и очищается при переходе на другую страницу.
- Сначала использовать возможности CSS и уже выбранного GSAP; отдельный движок 3D или дополнительная библиотека для этого эффекта не требуются.

Приёмка: проверить медленное и быстрое движение мыши, уход указателя, обе темы, изменение размеров, мобильный экран, reduced motion, кликабельность элементов hero и очистку после навигации. Это требование к будущей реализации; эффект пока не реализован.

## Порядок реализации и приёмка

1. Контракт обнаружения, валидатор пакетов, долговечное хранилище и GitHub-сканер с тестами на подмену, пагинацию, лимиты и повторное обнаружение.
2. Аккаунты, серверные роли, аудит, очередь и решения по отдельной ревизии. Тесты CSRF, сессий, запрета самопроверки и доступа без роли.
3. Публичный Next.js каталог, кабинеты, скачивание и RU/EN. Проверка обеих тем, телефона, клавиатуры, reduced-motion и прямых ссылок.
4. Добровольный каталог монитора и установка с закреплённым hash через прежний установщик. Тесты отсутствия egress при отключении, несовпадения digest, конфликта ID и недоступности marketplace.
5. Docker-маркер и релиз, документация автора/модератора/оператора, отдельный репозиторий marketplace, CI и развёртывание.

Сквозной критерий: реальный GitHub-релиз обнаружен → pending → модератор одобрил → версия появилась на сайте и в включённом каталоге монитора → обе загрузки возвращают идентичный JSON → агент установленного узла получает прежний протокол. Новая версия не публикуется без нового решения. Подмена asset не изменяет опубликованные байты. Перезапуск сохраняет все данные.

## Что потребуется от владельца для production

- Выбор сервера и подтверждение адреса marketplace; DNS и сертификат для нового поддомена.
- GitHub OAuth application, Google OAuth client и callback URL; секреты передаются через защищённую настройку сервера.
- Отправка писем для email-регистрации и восстановления.
- Чтение публичного GitHub с отдельным токеном для сканера, начальная административная учётная запись и список модераторов.

Эти настройки не нужны для тестов с подставными API, но необходимы для действительного production-входа. Неподключённый способ входа не выдаётся за работающий. Новые зависимости и службы согласовываются до добавления согласно правилам проекта.

## Технические решения Nest.js

- Turborepo 2.11.8 с npm workspaces: `apps/api`, `apps/web`, `packages/contracts`. По уточнению владельца фронтенд реализуется первым; Nest.js API и общие контракты следуют отдельным этапом.
- Node.js 24 LTS; PostgreSQL 18 с закреплённой поддерживаемой minor-версией и digest образа перед развёртыванием.
- Nest.js 12.1.3: `@nestjs/common`, `@nestjs/core`, `@nestjs/platform-express`; обязательные peer dependencies `reflect-metadata` и `rxjs`.
- `pg` 8.23.1 для PostgreSQL; SQL-миграции и параметризованные запросы.
- `openid-client` 6.8.8 для Google OIDC; GitHub OAuth использует проверяемый серверный flow с одноразовым state и PKCE. `nodemailer` 10.1.1 для SMTP. Секреты не передаются клиентским компонентам.
- TypeScript, Node test runner и `@nestjs/testing`; Prettier 3.9.10, ESLint, Playwright для сквозной проверки. Next.js 16.4.0, React 19.3.0, GSAP 3.15.0 и `@gsap/react` 2.1.2 сохраняют уже используемый стек интерфейса.
- Версии новых пакетов закрепляются в package-lock после согласования зависимостей. Версии Nest.js, pg, openid-client и nodemailer проверены через npm registry 14 октября 2026; наличие совместимой версии не заменяет сборку и тесты.
- Нативные ELF/PE-заголовки проверяет TypeScript-валидатор по существующему контракту Go. Максимальные длины строк считаются в UTF-8 байтах, чтобы не расходиться с Go на кириллице. Набор общих fixture-пакетов проходит обе реализации.
- Незавершённый цикл обнаружения возобновляется по данным PostgreSQL. Повторная обработка кандидата идемпотентна; ожидающие кандидаты остаются в базе, а не в памяти процесса.
- Сессии — случайные непрозрачные токены, в базе хранится digest. Проверка ролей выполняется по базе на каждом приватном запросе. JWT с долгоживущими ролями не используется.

## Проверенные основания

- Monitor: `backend/modules.go`, `lib/modules.ts`, `components/modules.tsx`, `docs/MODULES.md`; несовпадение неизвестных полей отвергается текущим установщиком.
- Docker: `manifest.json` и `scripts/build.ps1`; base64-сборки и внутренние digest уже включаются в JSON-пакет.
- Website: `next.config.mjs` и `.github/workflows/pages.yml`; текущий сайт — static export на Pages.
- [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) и [Release assets API](https://docs.github.com/en/rest/releases/assets): ID релизов/assets, source tag, метаданные и asset digest.
- [Nest.js: базы данных](https://docs.nestjs.com/techniques/database), [планировщик](https://docs.nestjs.com/techniques/task-scheduling), [Node.js scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

Граф Monitor использован для поиска символов; из-за изменившихся метаданных индекса выводы проверены по исходникам. Website и Docker не входят в этот граф и изучены напрямую.
